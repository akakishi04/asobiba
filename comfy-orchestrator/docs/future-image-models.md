# 次世代画像モデルの導入・検証計画

作成日: 2026-11-28  
状態: 計画のみ・導入保留  
基準コミット: `ac258ecf8dd5ae59287053278c62bda22980f437`

## 1. 目的と制約

現在の WAI / Anima / Qwen 系による画像生成を維持しながら、単なる画風や画質の違いではなく、新しい制御能力を獲得する。対象用途はイラスト制作の参考資料（キャラクター・衣装・体の形状・構図・布のしわ・光と影・素材感）。

- **ユーザーが改めて導入を指示するまで、ダウンロード、ComfyUI 更新、依存関係インストール、アプリ実装を開始しない。**
- Windows 11 / RTX 4070 Ti SUPER 16 GB / RAM 64 GB を想定。LM Studio と ComfyUI は既存のメモリ解放方針で順次利用する。
- 日本語の自然文入力を維持する。XML、JSON、座標やモデル固有のタグをユーザーが手書きすることを必須にしない。
- 既存の生成モデル登録、画像調整、履歴、比較生成、動画機能を壊さない。main 運用を継続し、各候補を個別に検証する。
- ローカル実行を優先する。外部 API 送信、追加課金、信頼性未確認のカスタムノードはユーザーの明示承認なしに導入しない。
- 公式記載のモデル能力は検証の出発点であり、当該 PC における速度・画質・VRAM 使用量を保証するものではない。ライセンスは重み・量子化版・追加 LoRA・依存物の実際の配布条件を導入時に確認する。

## 2. 導入順序

| 優先 | 候補 | 得たい能力 | 初回検証 | 導入時の主な障壁 |
|---|---|---|---|---|
| P1 | NewBie-image-Exp0.1 | 複数人物の属性分離・衣装指定 | アニメ T2I、タグ vs XML | 専用 XML、2 種類のテキストエンコーダー、FLUX VAE、非商用条件 |
| P2 | MOSS-Image | 領域・レイアウト・深度を利用した構図制御 | T2I → layout → color/depth | モデル固有の座標系、制御 LoRA、深度推定、VRAM、ComfyUI バージョン |
| P3 | HiDream-O1-Image | 外部 VAE なしの画素直接生成、参照画像条件付け | Dev の T2I → 参照画像編集 | 8B、量子化・オフロード、編集に適した checkpoint 選択 |
| P4 | NitroFusion2 | 1–2 ステップでラフ候補を高速生成 | 1 step → 2 step → Union ControlNet | ステップ固有のサンプリング、追加 LoRA / カスタムノードの監査 |
| P5 | MiniMax H3 Image | 高解像度・複数参照からの静止画生成と動画素材の接続 | T2I → 複数参照 → H3 動画素材 | H3 Image 固有の重み・VAE、6 step 固定、VRAM、解像度・参照番号 |
| P6 | FIBO 2.0 | 属性単位で再生成・編集できる構造化シーン記述 | VGL を手動作成 → ローカル LLM 変換 → 属性差分 | VGL スキーマ、標準変換の Gemini 依存、CC BY-NC 4.0、ネイティブ対応範囲 |

P1/P2 を先に検証する。P3 以降は P1/P2 の実測結果と実際の利用価値を見て着手する。FIBO は新しい UI・データ構造を必要とするため最後に置く。Qwen-Image-2.1 や既存系列の派生モデルは別の性能改善候補として保留し、本計画の対象に自動追加しない。

## 3. 候補別の検証・実装案（未着手）

### P1 NewBie

公式は 3.5B の Next-DiT 系アニメモデル。Gemma3-4B-it、Jina CLIP v2、FLUX.1-dev の 16ch VAE を使用。タグ・自然文・学習済み XML 形式を扱える。

- 公式 ComfyUI テンプレートで単一人物 T2I を確認し、次に二人の衣装・髪色・装飾品の取り違えを測る。同じモデル内でタグと公式 XML 形式を比較する。
- アプリは既存の日本語指示と承認済みキャラ特徴をモデル固有の XML に変換する。具体的な要素名、閉じタグの形式、人物の区切り方は公式ガイドを採用する。一般的な XML 構文や独自タグを憶測で使わない。
- 各人物の指定を個別に保持し、モデル間の比較には同じ意味内容を使用する。実際に実行された XML を履歴へ保存する。
- まず T2I のみ。既存 SDXL 用グラフや VAE は流用しない。配布元の非商用ライセンスを確認する。

参照: [ComfyUI 公式モデル](https://huggingface.co/Comfy-Org/NewBie-Image-Exp0.1) / [公式実装](https://github.com/NewBieAI-Lab/NewBie-image-Exp0.1) / [ComfyUI の XML 形式ガイド](https://github.com/Comfy-Org/docs/blob/main/tutorials/image/newbie-image/newbie-image-exp-0-1.mdx)

### P2 MOSS-Image

5B の DiT 系。ネイティブ対応とレイアウト入力を持つ。色領域・深度制御は追加の専用 control adapter LoRA を用いる。公式ドキュメント上の color/depth テンプレートは ComfyUI 0.43.0 以降を要求する。

- 量子化された T2I グラフを先に検証し、レイアウト指定は人物・物体の位置と前後関係に限定して試す。
- 次に既存の3Dデッサン素材・手描き領域マップから深度/色マップ制御を試す。色マップの色は領域 ID として扱い、出力色の指定と混同しない。解像度、座標系、近遠の明暗、マップのサイズ一致を検証する。
- MoGe 推定は任意段階とし、まず手持ちの制御マップでテストする。公式テンプレートの追加 encoder、制御 LoRA、MoGe の容量は導入時に確定する。
- 生成制御の強度・終了割合を比較し、元構図に過剰追従せず、衣装や陰影を変えられる設定を探す。領域/深度入力は元画像の I2I と別の入力役割として扱う。

参照: [公式実装](https://github.com/OpenMOSS/MOSS-Image) / [ComfyUI モデル](https://huggingface.co/Comfy-Org/MOSS-Image) / [公式テンプレートガイド](https://github.com/Comfy-Org/docs/blob/main/tutorials/image/moss-image/moss-image.mdx)

### P3 HiDream-O1-Image

8B の Pixel-level Unified Transformer。外部 VAE と独立した生成用テキストエンコーダーを持たない。公式 ComfyUI の FP8 版を候補にし、追加のプロンプト拡張用 LLM は必須かを別途確認する。

- Dev を T2I の候補にする。参照編集は公式が推奨する Full を優先検証する。公式ガイドの 28/50 step は版ごとの出発点であり固定値と断定しない。
- 画素直接生成を既存の潜在拡散系ノードへ強制的に当てはめない。参照画像の用途（人物維持/編集）とプロンプトを明示的に分離する。
- 衣装の細線、金具、布の質感、目元の描写と、参照画像からポーズを変更した際の保持率を評価する。FP8 の実測 VRAM・速度で採否を判断する。

参照: [モデル](https://huggingface.co/HiDream-ai/HiDream-O1-Image-Dev) / [ComfyUI 公式ガイド](https://github.com/Comfy-Org/docs/blob/main/tutorials/image/hidream/hidream-o1.mdx)

### P4 NitroFusion2

Z-Image-Turbo を基盤とした 1–2 step 蒸留モデル。公式には 1/2 step ワークフローと Union ControlNet が公開されている。

- まず 1 step T2I の実時間を測る。2 step の de-distillation LoRA、追加ノード、低ビット量子化は公式設定・実装を監査した後に比較する。
- 低ステップで手、金具、模様、布のしわ、陰影が破綻しないかを確認する。速さだけで採用しない。
- 採用後も最終品質用モデルの代替を前提にせず、ラフを短時間で複数生成する候補とする。必要なら既存の素材転送から本生成モデルへつなぐ。
- Union ControlNet は別段階。最初の導入には含めない。

参照: [公式実装・ワークフロー](https://github.com/ChenDarYen/NitroFusion2) / [公式 Union ControlNet](https://huggingface.co/ChenDY/NitroFusion2-Controlnet-Union)

### P5 MiniMax H3 Image

公式 ComfyUI は T2I/参照編集を同一 checkpoint で扱い、6 step・guidance 1 の蒸留設定と高解像度出力に対応する。H3 動画用 Qwen3-VL encoder と共有できる可能性があるが、実際のファイル互換性を確認する。動画用 VAE の流用は仮定しない。

- 公式テンプレートの許容する低めの解像度から開始し、16GB 環境のピーク負荷を確認する。最初から4K・16枚参照を試さない。
- 参照編集では image_1（編集元）と他の参照画像を区別し、番号とプロンプトの対応を固定する。参照画像は2枚から評価する。
- 固定 step/CFG、負のプロンプト非対応など、モデル固有の制約を UI と比較生成で尊重する。
- 生成した静止画を既存の H3 動画開始フレームや参照画像として利用する。動画側の VAE・連続生成処理は変更しない。

参照: [ComfyUI 公式発表](https://blog.comfy.org/p/minimax-h3-image-is-now-available) / [ComfyUI 配布](https://huggingface.co/Comfy-Org/MiniMax-H3-Image)

### P6 FIBO 2.0

8.1B の生成部と Qwen3-VL のテキストエンコーダー。自然文を直接与えるのではなく、モデルが学習した VGL 構造化 JSON を利用する。公式の bria-vgl 変換は Gemini API を使用するため、ローカル LLM による同等構造の作成は独立した検証課題とする。

- 公式スキーマの最小シーンを用いて T2I を試し、次に光源、服の材質、カメラ等を一項目だけ変更する。
- JSON Schema とホスト側検証で形式を担保し、編集は部分差分として保存する。公式スキーマと異なる簡易 JSON をそのまま渡さない。
- Gemini API や有償サービスを無断利用しない。ローカルで成立しない場合は保留。ComfyUI 接続方式、追加ノード、重み・VAE・フォント等の依存関係も確認する。
- 非商用ライセンスの制約を記録する。既存の単純な自然文 UI を置き換えることはしない。

参照: [公式モデル・ライセンス・VGL](https://huggingface.co/briaai/Fibo-2.0-dev) / [Diffusers の実装ガイド](https://huggingface.co/docs/diffusers/en/api/pipelines/bria_fibo2)

## 4. 共通検証セット

導入を再開したら、各ケースを固定した日本語指示と 3 Seed（例: 123, 456, 789）で比較する。初回は 1024×1024 相当、各モデルの正式なサイズ制約と推奨値に従い、適合しない場合は別枠に記録する。Seed の一致は異なるアーキテクチャ間で同一構図/初期潜在を保証しない。

| ID | 内容 | 評価 |
|---|---|---|
| C01 | 単一人物、複数の指定色と服の層、金具・装飾、左右差 | 指定属性の正答数 / 指定属性数 |
| C02 | 二人の人物、異なる髪色・服・左右の位置 | 人物間の属性混入、位置の正答 |
| C03 | 全身、座り姿勢、斜め視点、手足と遮蔽 | 構図、人体、意図しない欠損 |
| C04 | 同一形状の布を綿・絹・革で比較 | 材質、張力、しわ、光の反射 |
| C05 | 同一衣装で光源方向のみ変更 | 陰影の整合性、意図しない衣装変更 |
| C06 | 参照画像からポーズまたは背景だけ変更 | キャラ・衣装維持率、指定変更の成否 |
| C07 | 3D素材または手描きの構図/深度指定 | 位置、シルエット、前後関係 |
| C08 | 高速生成の複数案 | 許容画質の画像割合、1枚/候補集合の所要時間 |

C01～C05 を基本比較にする。C06～C08 は該当機能を持つ候補の専用検証。モデルが未対応の機能は失敗ではなく N/A と記録する。評価はユーザーによる視覚確認を主とし、VLM の自動採点のみで採否を決めない。固有キャラクター名に依存しない自作の服装指定を使い、学習データの知識と属性追従を区別する。

保存する測定項目: モデル/ファイル名・SHA256・ライセンス・ComfyUI の版・公式グラフ参照・実行プロンプト・Seed・サイズ・sampler/scheduler/step/CFG・初回ロード時間・ウォーム生成時間・ピーク VRAM/RAM・LLM 入出力トークン・生成失敗・視覚評価・採否理由。既存の比較画面（最大4モデル）を利用し、必要なら複数グループに分ける。

## 5. アプリの対応方針

今回の計画段階では実装しない。将来はモデル追加ごとに以下の最小差分を検討する。

1. 公式 API ワークフローから、モデル固有のノード・入力・ファイル・固定設定を抽出し、既存の workflow registry / model profiles / model registry へ新しいアダプターとして登録する。未知の系列を既存の Anima/SDXL 等と誤認させない。
2. 既存のタグ・自然文を共通の意味情報として保ち、XML、VGL、参照番号付きプロンプト等は必要なモデルに限って追加で構築する。共通プロンプト生成とモデル固有の構文変換を区別し、追加 LLM 呼び出しとトークンを計測する。MOSS のレイアウト/マップは画像プロンプトとは別に管理する。
3. 履歴に実行時の形式とバージョン、入力役割、参照順序、固定値、実際の実行グラフを追跡できる情報を保存する。過去データは変更しない。キャッシュは形式・スキーマ・変換方針で区別する。
4. 画像比較は意味内容、可能な共通サイズ・Seed、各モデルの推奨設定を揃える。固定蒸留モデルの条件は無理に統一しない。必要な形式や入力が欠ける場合は比較開始前に停止し、暗黙のモデル切替をしない。
5. GUI は既存の生成モデル選択と画像調整を維持し、モデル固有の入力が必要な時のみ表示する。手動モデル登録は既知の互換アダプターに限定する。
6. オフラインの設定/グラフ/スキーマ/履歴/再生/比較/キャンセルのテストと実機検証を行う。未知ジョブの自動再投入や並列生成は行わない。

## 6. 着手と採否のゲート

- G0（現在）: 計画承認・保留。追加実装やモデル取得はしない。
- G1: ユーザーの再開指示後、対象1件の公式リンク、重みの配布条件、必要容量、公式ワークフロー、ComfyUI 対応版、依存関係を再確認。ダウンロード対象を確定する。
- G2: 既存環境を壊さない方法で公式グラフの単発生成を確認する。まず1枚、その後3 Seed。VRAM不足や依存関係の競合がある場合は量子化/オフロードを検討し、改善できなければ保留。
- G3: 共通比較ケースで、既存モデルと異なる実用上の価値があるか確認。暫定採用条件は、主目的のケースで既存最良モデルに対して改善が見られ、他の品質・運用上の重大な劣化がないこと。比較不能なら保留し、数値を推測で補わない。
- G4: 採用決定後にのみアプリへ最小限の対応を実装。既存ワークフロー・履歴の回帰テストを行い、main に記録する。
- G5: 実運用で有益かを再評価し、次のモデルへ進む。使わないモデルを際限なく追加しない。

**現時点での最初の着手候補は NewBie。次は MOSS-Image。導入時期、具体的な checkpoint/量子化、容量、速度の数値は未確定。自動着手しない。**
